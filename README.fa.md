# یکپارچه‌سازی Snort 3 روی ویندوز

🌐 [English version](README.md)

محیط بیلد و یکپارچه‌سازی ویندوز برای [Snort 3](https://github.com/snort3/snort3) و [LibDAQ](https://github.com/snort3/libdaq).

این مخزن یک یکپارچه‌سازی بازتولیدپذیر از Snort 3 و LibDAQ روی ویندوز فراهم می‌کند، شامل تغییرات سازگاری مخصوص ویندوز که برای بیلد Snort، بارگذاری ماژول‌های DAQ، ضبط ترافیک زنده شبکه از طریق Npcap و اجرای قوانین تشخیص Snort لازم است.

این مخزن حول دو تغییر مستقل upstream طراحی شده است:

- پشتیبانی ویندوز برای Snort 3
- پشتیبانی بارگذاری داینامیک ماژول در LibDAQ روی ویندوز

این دو تغییر عمداً به‌صورت دو pull request مستقل در upstream نگه داشته می‌شوند و می‌توانند مستقل از هم استفاده شوند.

# نمای کلی

Snort 3 یک فریم‌ورک تشخیص و جلوگیری از نفوذ شبکه است که اساساً برای محیط‌های شبه‌یونیکس طراحی شده است.

LibDAQ کتابخانه Data Acquisition است که Snort با آن دریافت پکت را از مکانیزم ضبط زیرین جدا می‌کند.

روی سیستم‌های شبه‌یونیکس، Snort و LibDAQ به تعدادی API و فرض خاص POSIX تکیه می‌کنند، از جمله:

- بارگذاری داینامیک کتابخانه در POSIX
- سوکت‌های Unix domain
- قابلیت‌های فایل‌سیستم مخصوص یونیکس
- APIهای سیگنال و همگام‌سازی POSIX
- رفتار شبکه‌ای مخصوص یونیکس
- APIهای خطا و زمان POSIX
- تارگت‌های بیلد مخصوص یونیکس
- ماژول‌های داینامیک با پسوند `.so`

ویندوز برای چند مورد از این مکانیزم‌ها API و رفتار زمان‌اجرای متفاوتی دارد.

هدف این مخزن فراهم کردن همان کار سازگاری مخصوص ویندوز است که لازم است تا Snort 3 و یکپارچه‌سازی DAQ آن در محیط ویندوز درست کار کنند.

این یکپارچه‌سازی روی این محیط تست شده است:

- Windows 10 Enterprise نسخه ۶۴ بیتی
- MSYS2 UCRT64
- Snort 3.12.2.0
- LibDAQ 3.0.27
- Npcap 1.88

سیستم حاصل روی ترافیک زنده شبکه اعتبارسنجی شد.

این مستندات به هیچ آدرس خصوصی شبکه، GUID اینترفیس، نام کاربری یا مسیر فایل‌سیستم خاص یک ماشین نیاز ندارد.

---

# چرا این مخزن وجود دارد

این مخزن قرار نیست جایگزین پروژه‌های upstream یعنی Snort یا LibDAQ شود.

در عوض سه هدف دارد:

1. فراهم کردن یک محیط بیلد و یکپارچه‌سازی ویندوز که بازتولیدپذیر باشد.
2. نگه داشتن تغییرات مخصوص ویندوز تا وقتی بررسی upstream در جریان است.
3. نشان دادن این که Snort 3 و LibDAQ می‌توانند با Npcap روی ویندوز کنار هم کار کنند.

این پروژه همچنین دو مسئله قابل‌حمل بودن (portability) را از هم جدا می‌کند.

Snort به سازگاری ویندوز در بخش نسبتاً بزرگی از درخت سورس خود نیاز دارد.

نیاز ویندوزی LibDAQ خیلی محدودتر است: کشف و بارگذاری داینامیک ماژول DAQ.

جدا نگه داشتن این تغییرات باعث می‌شود بررسی هر دو پروژه راحت‌تر شود و هر تغییر مستقل قابل استفاده باشد.

# معماری

این یکپارچه‌سازی سه جزء اصلی دارد:

```text
                    Windows 10
                        |
                        |
                     Npcap
                        |
                        v
                 DAQ pcap module
                  daq_pcap.dll
                        |
                        v
                     LibDAQ
                  (DAQ 3.0.27)
                        |
                        v
                     Snort 3
                  (3.12.2.0)
                        |
                        v
                Detection Engine
                        |
                        v
                    Alerts
```

مسئولیت‌ها این‌طور جدا شده است.

### Npcap

Npcap قابلیت ضبط پکت روی ویندوز می‌دهد.

### LibDAQ

LibDAQ برای Snort یک لایه انتزاعی روی دریافت پکت می‌دهد.

ماژول DAQ نسخه pcap با Npcap صحبت می‌کند.

### Snort

Snort ماژول DAQ را بار می‌کند، پکت‌ها را می‌گیرد، از موتورهای بازرسی و تشخیص عبور می‌دهد و هشدار تولید می‌کند.

# اجزای مستقل upstream

تغییرات Snort و LibDAQ عمداً مستقل‌اند.

## پشتیبانی ویندوز در Snort 3

تغییرات Snort سازگاری ویندوز را در سراسر درخت سورس Snort می‌دهد.

از جمله این حوزه‌ها:

- پیکربندی CMake
- شبکه‌بندی ویندوز
- مدیریت پردازه
- نخ‌ها (threading)
- مدیریت فایل‌سیستم
- لاگ‌گیری
- بارگذاری پلاگین
- APIهای خاص پلتفرم
- کانکتورهای مخصوص یونیکس
- ترانسپورت‌های مخصوص یونیکس
- مدیریت زمان
- مدیریت خطا
- تطبیق wildcard
- ماژول‌های داینامیک
- چک‌های بیلد مربوط به RPC
- نیازهای لینکر ویندوز

این کار مستقل به مخزن Snort سابمیت شده است.

## پشتیبانی ویندوز در LibDAQ

تغییرات LibDAQ مسئله بارگذاری داینامیک ماژول DAQ را حل می‌کند.

پیاده‌سازی ویندوز از این‌ها استفاده می‌کند:

```text
LoadLibraryA()
GetProcAddress()
FreeLibrary()
```

به‌جای نسخه POSIX:

```text
dlopen()
dlsym()
dlclose()
```

رفتار POSIX موجود روی سیستم‌های غیر ویندوز همچنان در دسترس است.

این کار مستقل به مخزن LibDAQ سابمیت شده است.

# نحوه کار یکپارچه‌سازی

یکپارچه‌سازی این زنجیره وابستگی را دنبال می‌کند:

```text
Snort
  |
  | DAQ API
  v
LibDAQ
  |
  | pcap DAQ module
  v
daq_pcap.dll
  |
  | packet capture API
  v
Npcap
  |
  v

```

خود Snort لازم نیست جزئیات سطح پایین پیاده‌سازی ضبط پکت ویندوز را بداند.

LibDAQ لایه انتزاع را می‌دهد.

ماژول DAQ نسخه pcap با Npcap صحبت می‌کند و پکت‌های ضبط‌شده را به Snort می‌دهد.

این جداسازی مهم است چون پشتیبانی ویندوز یک تغییر یکپارچه و یک‌تکه نیست.

# جزئیات تغییرات ویندوز

# Snort 3

کامیت windows-support در Snort چند حوزه وابسته به پلتفرم را تغییر می‌دهد.

تغییرات در ادامه بر اساس کارکرد گروه‌بندی شده‌اند.

---

## ۱. پشتیبانی بیلد و لینکر ویندوز

چند فرض بیلد مخصوص یونیکس روی ویندوز صدق نمی‌کند.

پس بیلد ویندوز مدیریت CMake مخصوص پلتفرم اضافه می‌کند.

مثلاً Snort روی ویندوز به این لینک می‌شود:

```text
ws2_32
```

`ws2_32` همان APIهای شبکه Winsock ویندوز است که کدهای مربوط به شبکه به آن نیاز دارند.

اگزکیوتیبل ویندوز همچنین به مدیریت مناسب سمبل/export برای ماژول‌های داینامیک نیاز دارد.

پس پیکربندی CMake ویندوز این را به تنظیمات لینکر اضافه می‌کند:

```text
--export-all-symbols
```

تارگت‌های آبجکت مخصوص یونیکس هم هر جا کاربردی ندارند از اگزکیوتیبل ویندوز حذف می‌شوند.

این کار اجازه می‌دهد بیلد ویندوز از همان معماری کلی Snort استفاده کند، بدون این که به وابستگی‌هایی نیاز داشته باشد که فقط روی سیستم‌های شبه‌یونیکس هست.

---

## ۲. مدیریت ترانسپورت‌های مخصوص یونیکس

Snort اجزای ترانسپورت دارد که به قابلیت مخصوص یونیکس وابسته‌اند.

مثلاً:

```text
mp_unix_transport
```

برای بیلد native ویندوز مناسب نیست.

پس بیلد ویندوز این آبجکت مخصوص یونیکس را از اگزکیوتیبل حذف می‌کند.

این کار باعث نمی‌شود بیلدهای ویندوز مجبور باشند قابلیتی را فراهم کنند که فقط روی سیستم‌های یونیکس هست.

---

## ۳. کانکتورهای Unix Domain

کانکتورهای Unix domain به مکانیزم IPC مخصوص یونیکس وابسته‌اند.

ویندوز همان پیاده‌سازی سوکت Unix-domain را که کد موجود Snort انتظار دارد نمی‌دهد.

پس لودر کانکتور روی ویندوز از بارگذاری پیاده‌سازی‌های کانکتور مخصوص یونیکس خودداری می‌کند.

از جمله:

```text
tcp_connector
unixdomain_connector
```

که پیاده‌سازی‌های موجودشان به قابلیت مخصوص یونیکس وابسته است.

آبجکت‌های آماری متناظرِ خاص پلتفرم هم برای کامپایل ویندوز به‌درستی مدیریت می‌شوند.

هدف حذف فریم‌ورک کانکتور نیست، بلکه جلوگیری از این است که اجزای پشتیبانی‌نشده مخصوص یونیکس بیلد ویندوز را خراب کنند.

---

## ۴. لاگر سوکت یونیکس

لاگر `alert_unixsock` به سوکت‌های Unix-domain وابسته است.

پس از بیلدهای ویندوز حذف می‌شود.

پیکربندی CMake این لاگر را فقط روی پلتفرم‌های غیر ویندوز اضافه می‌کند.

این کار لاگر موجود را روی سیستم‌های یونیکس حفظ می‌کند و در عین حال جلوی خراب شدن بیلد ویندوز توسط یک وابستگی پشتیبانی‌نشده را می‌گیرد.

---

## ۵. سازگاری API زمان

Snort روی سیستم‌های POSIX از این استفاده می‌کند:

```text
ctime_r()
```

ویندوز به‌جایش این را می‌دهد:

```text
ctime_s()
```

پس کد ویندوز از این استفاده می‌کند:

```c
ctime_s(time_buf, sizeof(time_buf), &now);
```

و در عین حال این را حفظ می‌کند:

```c
ctime_r(&now, time_buf);
```

برای پلتفرم‌های غیر ویندوز.

این یک تطبیق قابلیت‌حمل (portability) است نه بازطراحی رفتاری.

---

## ۶. مدیریت رشته خطا

بعضی کدهای POSIX از این استفاده می‌کنند:

```text
strerror_r()
```

در حالی که ران‌تایم مایکروسافت معادل امن همین عملیات رشته خطا را می‌دهد:

```text
strerror_s()
```

پس شاخه‌های مخصوص ویندوز هر جا لازم است از `strerror_s()` استفاده می‌کنند.

پیاده‌سازی POSIX موجود دست‌نخورده می‌ماند.

این رویکرد تفاوت‌های API خاص پلتفرم را پشت کامپایل شرطی ایزوله نگه می‌دارد.

---

## ۷. دسترسی به فایل

بعضی قابلیت‌های فایل DAQ موقع باز کردن فایل از این استفاده می‌کرد:

```text
O_NONBLOCK
```

این رفتار مستقیماً به پیاده‌سازی ویندوز قابل‌حمل نیست.

پس مسیر ویندوز از این استفاده می‌کند:

```text
open(filename, O_RDONLY)
```

در حالی که پیاده‌سازی POSIX همان را نگه می‌دارد:

```text
open(filename, O_RDONLY | O_NONBLOCK)
```

این رفتار اصلی را برای سیستم‌های شبه‌یونیکس نگه می‌دارد و در عین حال اجازه می‌دهد جزء فایل DAQ زیر ویندوز کامپایل و کار کند.

---

## ۸. تطبیق wildcard در فایل‌سیستم

Snort قبلاً برای تطبیق wildcard به این تکیه می‌کرد:

```text
fnmatch.h
```

آن هدر/API روی ویندوز به همان شکل عموماً در دسترس نیست.

پس یک پیاده‌سازی داخلی کوچک wildcard معرفی شد.

این پیاده‌سازی معنای wildcard مورد نیاز کد Snort را پشتیبانی می‌کند، از جمله:

```text
*
?
```

کد مخصوص ویندوز وابستگی به `fnmatch()` را با این جایگزین می‌کند:

```text
wildcard_match()
```

این پردازش wildcard را داخل درخت سورس Snort نگه می‌دارد و وابستگی خارجی اضافه مخصوص ویندوز معرفی نمی‌کند.

---

## ۹. همگام‌سازی فایل امن در برابر سیگنال

بعضی کدهای یونیکس از این استفاده می‌کنند:

```text
fsync()
```

برای همگام‌سازی دیسکریپتورهای فایل.

پیاده‌سازی ویندوز همان معنای POSIX را از طریق همان API نمی‌دهد.

پس مسیر ویندوز از فراخوانی پیاده‌سازی یونیکس `fsync()` در مسیر لاگر امن‌دربرابر-سیگنالِ تحت‌تأثیر خودداری می‌کند.

پیاده‌سازی POSIX موجود دست‌نخورده می‌ماند.

---

## ۱۰. چک بیلد RPC

سیستم بیلد Snort وجود پیاده‌سازی دیتابیس برنامه RPC را چک می‌کند.

روی سیستم‌های شبه‌یونیکس این می‌تواند شامل این باشد:

```text
getrpcent()
```

و احتمالاً:

```text
TIRPC
```

ویندوز همان اینترفیس دیتابیس برنامه RPC یونیکس را نمی‌دهد.

پس بیلد ویندوز آشکارساز سرویس RPC تحت‌تأثیر را غیرفعال می‌کند، به‌جای این که نبود قابلیت RPC یونیکس را خطای کشنده پیکربندی بداند.

این اجازه می‌دهد بقیه Snort روی ویندوز با موفقیت بیلد شود.

---

## ۱۱. سازگاری `ffs()`

کد قبلاً از این استفاده می‌کرد:

```text
ffs()
```

برای پیدا کردن اولین بیت setشده.

پیاده‌سازی سازگار با ویندوز از این استفاده می‌کند:

```text
__builtin_ffs()
```

که تول‌چین GCC محیط MSYS2 UCRT64 آن را می‌دهد.

این از وابستگی به پیاده‌سازی POSIX تابع `ffs()` جلوگیری می‌کند.

---

## ۱۲. مدیریت پلاگین و ماژول ویندوز

Snort به‌شدت به ماژول‌هایی تکیه دارد که داینامیک بار می‌شوند.

پس بیلد ویندوز به مدیریت مناسب ماژول‌های داینامیک و دیده‌شدن سمبل نیاز دارد.

پیکربندی بیلد برای پشتیبانی از محیط ماژول‌داینامیک ویندوز تنظیم شد، در حالی که معماری ماژول موجود حفظ شد.

این به‌ویژه مهم است چون خود لایه DAQ هم داینامیک بار می‌شود.

---

## ۱۳. آمار thread-local

بعضی ماژول‌های کانکتور آمار را با حافظه thread-local تعریف می‌کنند.

کامپایلر/تول‌چین ویندوز لازم دارد تعریف‌های مناسب وجود داشته باشند وقتی پیاده‌سازی یونیکس عادی کامپایل نمی‌شود.

پس برای آمار کانکتورهای تحت‌تأثیر تعریف‌های مخصوص ویندوز اضافه شد.

این اجازه می‌دهد ماژول‌ها بدون نیاز به فایل‌های پیاده‌سازی مخصوص یونیکس کامپایل شوند.

---

## ۱۴. شبکه‌بندی ویندوز

شبکه‌بندی ویندوز از Winsock استفاده می‌کند.

پس بیلد ویندوز به این لینک می‌شود:

```text
ws2_32
```

این سمبل‌های شبکه‌ای مورد نیاز Snort و اجزای سازگار با ویندوزش را می‌دهد.

کد خاص پلتفرم با چک‌های ویندوز مثل این محافظت می‌شود:

```c
#ifdef _WIN32
```

تا پیاده‌سازی ویندوز جایگزین پیاده‌سازی یونیکس نشود.

---

## ۱۵. انتخاب سورس CMake مخصوص ویندوز

یک الگوی تکرارشونده در همه تغییرات، انتخاب شرطی سورس است.

به‌جای تلاش برای کامپایل هر فایل سورس یونیکس روی ویندوز، CMake اجزایی را که APIهای پلتفرم زیرین‌شان در دسترس نیست حذف می‌کند.

به‌صورت مفهومی:

```text
                    Snort source tree
                           |
              +------------+------------+
              |                         |
           Windows                   POSIX
              |                         |
       Windows-compatible         Existing Unix
          components                components
              |                         |
              +------------+------------+
                           |
                    Snort executable
```

این رویکرد تغییرات رفتاری در پیاده‌سازی غیر ویندوزی موجود را کمینه می‌کند.

# LibDAQ

تغییر ویندوز در LibDAQ عمداً خیلی کوچک‌تر است.

مسئله اصلی بارگذاری داینامیک ماژول است.

---

## ۱. بارگذاری داینامیک در POSIX

روی سیستم‌های شبه‌یونیکس LibDAQ از این‌ها استفاده می‌کند:

```c
dlopen()
dlsym()
dlclose()
dlerror()
```

این APIها از مدل سنتی بارگذاری‌داینامیک POSIX/لینوکس می‌آیند.

ویندوز این APIها را به همان شکل نمی‌دهد.

---

## ۲. بارگذاری داینامیک در ویندوز

ویندوز بارگذاری داینامیک کتابخانه را از طریق این‌ها می‌دهد:

```text
LoadLibraryA()
GetProcAddress()
FreeLibrary()
```

پیاده‌سازی ویندوز در LibDAQ یک لایه انتزاع معرفی می‌کند:

```text
daq_dlopen()
daq_dlsym()
daq_dlclose()
daq_dlerror()
```

روی ویندوز این wrapperها به APIهای لودر ویندوز نگاشت می‌شوند.

روی پلتفرم‌های غیر ویندوز به این‌ها نگاشت می‌شوند:

```text
dlopen()
dlsym()
dlclose()
dlerror()
```

این یک اینترفیس مشترک برای بقیه LibDAQ می‌سازد.

---

## ۳. چرا انتزاع مهم است

بدون این انتزاع، سورس LibDAQ باید در هر جایی که یک ماژول داینامیک باز یا بسته می‌شود منطق مخصوص ویندوز می‌داشت.

در عوض، رفتار خاص پلتفرم ایزوله شده است.

به‌صورت مفهومی:

```text
                 LibDAQ
                    |
             daq_dlopen()
                    |
          +---------+---------+
          |                   |
       Windows             POSIX
          |                   |
   LoadLibraryA()          dlopen()
```

همین الگو برای lookup سمبل و unload ماژول هم استفاده می‌شود.

این کد خاص پلتفرم را در بقیه LibDAQ کم می‌کند.

---

## ۴. پسوند ماژول داینامیک

ماژول‌های DAQ در یونیکس از این استفاده می‌کنند:

```text
.so
```

ماژول‌های داینامیک ویندوز از این استفاده می‌کنند:

```text
.dll
```

پس منطق کشف ماژول DAQ روی ویندوز از این استفاده می‌کند:

```text
.dll
```

و روی سیستم‌های POSIX همان را نگه می‌دارد:

```text
.so
```

این لازم است تا LibDAQ بتواند این را در پوشه ماژول DAQ ویندوز کشف کند:

```text
daq_pcap.dll
```

---

## ۵. گزارش خطای ویندوز

وقتی یک عملیات بارگذاری‌داینامیک ویندوز شکست می‌خورد، پیاده‌سازی کد خطای ویندوزِ گرفته‌شده از این را ثبت می‌کند:

```text
GetLastError()
```

بعد خطا از طریق انتزاع LibDAQ بیرون داده می‌شود.

این اطلاعات تشخیصی مفید می‌دهد و در عین حال ساختار گزارش خطای موجود در LibDAQ حفظ می‌شود.

---

## ۶. چرخه عمر ماژول داینامیک

پیاده‌سازی مخصوص ویندوز کل چرخه عمر ماژول داینامیک را پوشش می‌دهد:

```text
Discover module
      |
      v
daq_dlopen()
      |
      v
LoadLibraryA()
      |
      v
Get module handle
      |
      v
daq_dlsym()
      |
      v
GetProcAddress()
      |
      v
Use DAQ module
      |
      v
daq_dlclose()
      |
      v
FreeLibrary()
```

این مهم است چون صرف کامپایل `daq_pcap.dll` کافی نیست.

LibDAQ باید بتواند ماژول را درست کشف، بار، resolve سمبل و unload کند.

# چرا تغییرات Snort و LibDAQ جدا هستند

با این که Snort و LibDAQ کنار هم استفاده می‌شوند، مسئله قابل‌حمل بودنشان فرق دارد.

کار ویندوز در Snort مجموعه وسیعی از فرض‌های پلتفرم را در سراسر اپلیکیشن پوشش می‌دهد.

کار ویندوز در LibDAQ اساساً مربوط به بارگذاری ماژول داینامیک و کشف ماژول است.

پس:

```text
Snort Windows Support
        |
        +---- independent change
        |
        v
Snort application
```

و:

```text
LibDAQ Windows Support
        |
        +---- independent change
        |
        v
DAQ module loading
```

استک یکپارچه هر دو را ترکیب می‌کند:

```text
Snort Windows Support
          +
LibDAQ Windows Support
          +
Npcap
          =
Working Windows integration
```

اما هیچ‌کدام از تغییرات upstream از نظر مفهومی به این وابسته نیست که دیگری در همان کامیت یا pull request مرج شود.

این جداسازی بررسی upstream را هم راحت‌تر می‌کند.

```bash
./configure \
  --prefix=/path/to/snort3-windows/install \
  --disable-shared \
  --enable-static \
  --disable-afpacket-module \
  --disable-bpf-module \
```

```bash
make -C api
```

ماژول‌های DAQ را بیلد کنید:

```bash
make -C modules
```

API را نصب کنید:

```bash
make -C api install
```

ماژول‌ها را نصب کنید:

```bash
make -C modules install
```

نصب، هدرها و کتابخانه‌های LibDAQ مورد نیاز Snort را می‌دهد.

# بیلد ماژول DAQ نسخه pcap

یکپارچه‌سازی ویندوز لازم دارد ماژول DAQ نسخه pcap به‌صورت کتابخانه داینامیک ویندوز در دسترس باشد.

ماژول حاصل این است:

```text
daq_pcap.dll
```

این ماژول با کتابخانه ضبط پکت Npcap بیلد می‌شود.

پوشه ماژول مورد نیاز این است:

```text
install/lib/daq/
```

بعد از بیلد ماژول DAQ نسخه pcap، آن را داخل پوشه ماژول DAQ کپی کنید:

```bash
mkdir -p /path/to/snort3-windows/install/lib/daq

cp modules/pcap/.libs/daq_pcap.dll \
   /path/to/snort3-windows/install/lib/daq/
```

DLL حاصل به ران‌تایم Npcap نیاز دارد، از جمله:

```text
wpcap.dll
```

و همین‌طور کتابخانه‌های ران‌تایم مورد نیاز ویندوز.

# Npcap

Npcap قابلیت ضبط پکت مورد استفاده ماژول DAQ نسخه pcap را می‌دهد.

محیط تست‌شده از این استفاده می‌کند:

```text
Npcap 1.88
```

Npcap باید قبل از این که بتوان ضبط زنده پکت را تست کرد روی هاست ویندوز نصب شده باشد.

Snort از طریق اینترفیس ضبط پکت Npcap به اینترفیس‌های شبکه ویندوز دسترسی دارد.

پس لایه DAQ این را دنبال می‌کند:

```text
Snort
  |
LibDAQ
  |
daq_pcap.dll
  |
Npcap
  |
Windows network interface
```

نام‌ها و شناسه‌های خاص ماشین عمداً در این مستندات نیامده است.

---

# اجرای Snort

بعد از نصب، ماژول‌های DAQ را تأیید کنید.

Snort باید بتواند ماژول DAQ ویندوز را کشف کند:

```text
daq_pcap.dll
```

یک تست موفق کشف ماژول خروجی معادل این داد:

```text
Loading modules in:
<installation-prefix>/lib/daq

Registered daq module: pcap
Found module daq_pcap.dll
ret = 0
module: pcap
```

این تأیید می‌کند که:

1. مسیر جستجوی DAQ درست است.
2. ماژول DAQ نسخه pcap دیده می‌شود.
3. LibDAQ می‌تواند DLL ویندوز را بار کند.
4. ماژول DAQ با موفقیت register می‌شود.

یک تست مستقیم لودر ویندوز هم تأیید کرد:

```text
LoadLibrary OK
DAQ_MODULE_DATA OK
```

این تأیید می‌کند که مسیر بارگذاری داینامیک ویندوز می‌تواند DLL مربوط به DAQ را بار کند و داده ماژول مورد انتظار را resolve کند.

# ضبط زنده

بعد از این که ماژول DAQ نصب شد و Npcap در حال اجراست، Snort می‌تواند یک اینترفیس شبکه Npcap را باز کند.

شناسه دقیق اینترفیس به ماشین ویندوز بستگی دارد و نباید در مستندات عمومی هاردکد شود.

یک تست موفق ضبط زنده نشان داد که این مسیر درست کار می‌کند:

```text
Snort
    |
    v
LibDAQ
    |
    v
daq_pcap.dll
    |
    v
Npcap
    |
    v
Live network traffic
```

# تست قانون تشخیص

یک قانون ساده ICMP برای اعتبارسنجی کل مسیر پردازش پکت استفاده شد.

مثال قانون:

```text
alert icmp any any -> any any
(
    msg:"ICMP ECHO REQUEST";
    itype:8;
    sid:1000001;
    rev:5;
)
```

این قانون پکت‌های ICMP Echo Request را مچ می‌کند.

یک ICMP Echo Request از هاست تست ویندوز به سمت گیت‌وی شبکه محلی تولید شد.

Snort پکت زنده را با موفقیت پردازش کرد و هشداری معادل این تولید کرد:

```text
[1:1000001:5] "ICMP ECHO REQUEST" {ICMP}
<test-host> -> <local-gateway>
```

آدرس‌های IP واقعی عمداً در این مخزن نیامده است.

این تست کل مسیر را اعتبارسنجی می‌کند:

```text
Generated ICMP packet
        |
        v
Windows network stack
        |
        v
Npcap
        |
        v
daq_pcap.dll
        |
        v
LibDAQ
        |
        v
Snort
        |
        v
ICMP detection rule
        |
        v
Alert
```

# محدودیت‌های فعلی

این پروژه را باید کار پشتیبانی پلتفرم ویندوز و یکپارچه‌سازی دانست، نه ادعای برابری کامل قابلیت‌ها بین ویندوز و هر محیط Snort شبه‌یونیکس.

بعضی قابلیت‌های Snort ذاتاً خاص پلتفرم‌اند.

پس بیلد ویندوز اجزایی را که به قابلیت مخصوص یونیکس وابسته‌اند حذف یا تطبیق می‌دهد، از جمله حوزه‌هایی مثل:

- قابلیت سوکت Unix-domain
- ترانسپورت‌های مخصوص یونیکس
- لاگ سوکت یونیکس
- APIهای خاص POSIX
- قابلیت RPC مخصوص یونیکس
- APIهای تطبیق فایل‌سیستم POSIX

هدف این تغییرات این است که بیلد اصلی Snort و مسیر ضبط پکت DAQ روی ویندوز کار کند، بدون این که پیاده‌سازی غیر ویندوزی موجود بی‌دلیل تغییر کند.

برای ادعای برابری کامل قابلیت ویندوز تست اضافه لازم است.

# توسعه با کمک هوش مصنوعی

بخش‌هایی از فرایند توسعه، دیباگ، تحلیل قابل‌حمل بودن، عیب‌یابی بیلد، مستندات و بازبینی کد با کمک ابزارهای هوش مصنوعی انجام شد.

کمک هوش مصنوعی به‌عنوان کمک توسعه استفاده شد، از جمله:

- شناسایی ناسازگاری‌های محتمل POSIX به ویندوز
- تحلیل خطاهای کامپایلر و لینکر
- پیشنهاد نگاشت‌های API خاص پلتفرم
- بازبینی کامپایل شرطی
- بررسی رفتار سیستم بیلد
- بررسی منطق بارگذاری ماژول داینامیک
- کمک به ساختار مخزن یکپارچه‌سازی
- بازبینی مستندات و گام‌های بازتولیدپذیری

کد حاصل صرفاً بر مبنای پیشنهادهای تولیدشده با هوش مصنوعی پذیرفته نشد.

پیاده‌سازی در محیط ویندوز هدف به‌صورت دستی بازرسی، بیلد، تست و بازبینی شد.

اعتبارسنجی شامل اجرای واقعی Snort، کشف ماژول DAQ، بارگذاری داینامیک DLL، ضبط زنده Npcap و یک تست تشخیص ICMP زنده بود.

پس کمک هوش مصنوعی بخشی از گردش کار توسعه بود، در حالی که پیاده‌سازی نهایی و نتایج تست در محیط هدف بازبینی و اعتبارسنجی شدند.

# بازتولیدپذیری

یکپارچه‌سازی طوری طراحی شده که یک توسعه‌دهنده دیگر بتواند محیط را بازتولید کند، بدون این که به ماشین اصلی تکیه کند.

مخزن از انتشار این‌ها خودداری می‌کند:

- آدرس‌های IP محلی
- آدرس‌های گیت‌وی
- GUIDهای اینترفیس شبکه
- نام‌های کاربری ویندوز
- مسیرهای فایل‌سیستم شخصی
- پیکربندی خاص ماشین

در عوض مستندات از placeholderهایی مثل این استفاده می‌کند:


و:

```text

```

این پروژه را بدون افشای جزئیات شبکه تست اصلی بازتولیدپذیر می‌کند.

# نتیجه‌گیری

این مخزن یک یکپارچه‌سازی در حال کار از Snort 3 و LibDAQ و Npcap روی ویندوز نشان می‌دهد.

کار به دو تغییر قابل‌حمل بودنِ مستقل تقسیم شده است:

```text
Snort Windows Support
        +
LibDAQ Windows Support
        +
Npcap
        |
        v
Snort 3 running on Windows
```

تغییرات Snort مجموعه وسیع‌تر مسائل سازگاری ویندوز را در سراسر درخت سورس Snort پوشش می‌دهد.

تغییرات LibDAQ بارگذاری کتابخانه داینامیک ویندوز را می‌دهد که برای کشف و بارگذاری ماژول‌های DAQ مثل این لازم است:

```text
daq_pcap.dll
```

یکپارچه‌سازی کامل روی Windows 10 Enterprise نسخه ۶۴ بیتی با MSYS2 UCRT64 و Npcap بیلد و تست شد.

اعتبارسنجی نهایی تأیید کرد:

- کامپایل موفق Snort
- کامپایل موفق LibDAQ
- بارگذاری موفق ماژول DAQ در ویندوز
- دسترسی موفق به اینترفیس Npcap
- ضبط موفق پکت زنده
- پردازش موفق قانون ICMP
- تولید موفق هشدار

تغییرات متناظر پشتیبانی ویندوز همچنین به‌صورت pull requestهای جدا در upstream سابمیت شده‌اند تا توسط مین‌تینرهای مربوطه مستقل بررسی شوند.
